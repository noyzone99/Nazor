# Native renderer comparison

Run `pwsh -NoProfile -File Scripts/Tests/compare-renderers.ps1` from the repository root. Windows x64, .NET 10 and a working hardware GPU are required. Results go to a fresh directory under `artifacts/renderer-comparison/`; existing directories are never overwritten. Options: `-Samples 120`, `-Warmup 30`, `-Repetitions 4`, `-OutputDirectory <new-path>`, `-SkipBuild`. The script exits on unavailable hardware, incomplete results, changed machine/runtime/DPI/font, incorrect card geometry or failed image probes. It does not change the caller's environment.

## Workload and isolation

Each fresh process shows the same 900×600 logical client area, with 80 rounded cards in eight columns: left/top margins 12, horizontal pitch 108, vertical pitch 48, card size 100×40, padding 6, radius 4. Both use the same private Fira Sans Regular file at 14 px with 20 px line height. The font hash and actual DPI are recorded. The fixtures assert all card bounds and text content. Before/after snapshots verify that content was drawn, every card changed color for paint, and every card grew for layout. Text output must change too; font rasterization/antialiasing defaults can differ and pixel-identical text is not required.

Scenarios update all 80 cards: `text` replaces fixed-width numeric labels; `paint` alternates two opaque background colors; `layout` alternates widths 100/104 while keeping positions fixed. Nazor uses its component reconciliation and NSS descendant rules; Avalonia uses retained controls and direct property assignments. This measures these normal fixture paths, including their different update costs, rather than isolating Skia or testing every application architecture. It excludes bindings, large scrolling trees, startup process launch and autonomous animation under a blocked UI thread.

Nazor runs through its native desktop host with strict `NAZOR_RENDERER=CPU/GPU`. Avalonia.Desktop is pinned to **12.1.6** in the independent `Nazor.Avalonia.Benchmarks` executable; its packages never enter the Nazor runtime dependency graph. Avalonia CPU allows only `Software`; GPU allows only `AngleEgl`, limits ANGLE to Direct3D 11 and requires an identified non-software adapter. GPU initialization cannot silently fall back to CPU. GPU device labels must agree after case/whitespace normalization; differing labels require checking adapter selection before comparing. Nazor GPU uses native WGL. Avalonia retains its normal Windows composition selection. Rendering-library versions are recorded too: the default package stacks currently resolve different SkiaSharp/HarfBuzzSharp versions. The API, library and presentation differences are reported, not normalized away. See [Avalonia Windows options](https://docs.avaloniaui.net/docs/platform-specific-guides/windows) and the [versioned platform source](https://github.com/AvaloniaUI/Avalonia/blob/12.1.6/src/Windows/Avalonia.Win32/Win32PlatformOptions.cs).

## Measurements

Both benchmark executables target .NET 10 LTS. The Nazor harness loads the NSS compiler in process; the Avalonia harness uses the same runtime for comparison.

One update is in flight. Nazor waits for `FramePresented` identifying a UI frame after the change; Avalonia waits for the corresponding composition batch's `Rendered` task, which completes after the render-thread target pass. The latter is intentionally not `Processed`, which only acknowledges deserialization. See the versioned [batch contract](https://github.com/AvaloniaUI/Avalonia/blob/12.1.6/src/Avalonia.Base/Rendering/Composition/Transport/Batch.cs) and [server completion](https://github.com/AvaloniaUI/Avalonia/blob/12.1.6/src/Avalonia.Base/Rendering/Composition/Server/ServerCompositor.cs).

Completion time includes scheduling, synchronization/presentation waits and UI notification. These callbacks have different backend scopes; neither measures physical scanout or GPU execution. CPU/software may complete without waiting for vertical synchronization while GPU completion waits. A lower completion time alone does not establish lower rendering cost or a faster framework.

CPU cost is total process CPU over all measured updates divided by their count, including worker/driver CPU time and background render-loop work during pacing waits. Closed-loop cases can have different update rates and therefore different background-cost amortization; this is not isolated rendering CPU time. Windows CPU accounting is coarse: use the default sample count/repetitions rather than interpreting short smoke-run CPU values. Managed allocations use `GC.GetTotalAllocatedBytes(precise: true)` over that same interval and include every thread plus the shared harness. Working set/private memory include native libraries, drivers, caches and buffers; they are snapshots, not managed leak or VRAM measurements. The synchronous mutation call is diagnostic only: deferred reconciliation/layout/rendering is excluded from that particular duration. First completion excludes process launch and is not a cold-start benchmark.

Both processes disable tiered compilation. Snapshots/readback, PNG encoding and final validation are outside measurement; the first capture precedes warmup. No forced collection is inserted during samples. Four repetitions rotate the order of all four renderer/framework cases, putting each case in every order position for each scenario. Runs are sequential. Avoid moving/resizing/occluding the windows or running another benchmark concurrently; record the power/display configuration when comparing different sessions.

`report.md` summarizes completion percentiles pooled across processes and median process CPU/allocation/memory values. `summary.json` includes every raw report, sample, backend/device/runtime/font identity, execution order, driver version and range of per-run completion medians. Preserve that directory when sharing results. Results are a local Windows baseline for these three workloads, not a universal Nazor/Avalonia ranking or evidence about Linux/macOS.

For a quick full-matrix correctness check use `-Samples 10 -Warmup 5 -Repetitions 1`. Meaningful measurements should use the defaults. The original headless budgets and `verify-renderers.ps1` Nazor-only benchmark remain separate.

Reports also retain passive GC memory counters: the current approximate managed bytes and the heap size, fragmentation and committed bytes reported by the last collection. These are not native memory or exact retained-object measurements. For separate diagnostic runs, `NAZOR_COMPARISON_MEMORY_PAUSE_MS=15000` pauses each executable after measuring and reading process counters, before serializing its report. `<output>.memory-ready` contains its PID for external page-map or dump collection. Accepted pauses are 1–60,000 ms. The normal runner does not set this variable. Do not use paused/profiled runs as timing results; the final timing matrix must run without profilers or pauses.
